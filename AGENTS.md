# AI Agent Operational Playbook — Capy Monorepo (`web/`, `app/`, `worker/`)

Capy is a multi-platform color-by-number suite (`https://github.com/shthed/capy`, production at `https://capypaint.com/`, PR previews at `https://shthed.github.io/capy/`). This file is auto-loaded every AI turn—keep it strictly AI-specific and let it grow as needed to maximize agent execution quality and accuracy over raw token savings. Shared technical guardrails (`web/`, `app/`, `worker/`), model selection, CI, and maintenance live in [`DEV.md`](./DEV.md) (read [`DEV.md` Section 5](./DEV.md#5-core-technical-guardrails-web--app) before editing code); Project Management, Agile backlog governance, PR sync rules, and Release Promotion live in [`PROJECT.md`](./PROJECT.md).

## 1. AI Golden Invariants (Non-Negotiable Agent Guardrails)

1. **Never merge without approval, protect `main` via `beta`, & always check merge conflicts**: Never merge a PR or push directly to `main` or `beta` without explicit user confirmation (except approved [`AGENTS.md`](./AGENTS.md) updates pushed directly to `main` immediately using Repository admin bypass, then back-merged into `beta`). All daily feature/bugfix PRs branch from and target **`beta`** (`--base beta`, deploying `/capy/beta/` on merge) so live production players on `https://shthed.github.io/capy/` (`main`) are never disrupted; only human-requested **Release Promotion PRs (`beta -> main`)** target `main`. On every PR open/update and before requesting merge approval, fetch the target base (`git fetch origin beta main`) and run `gh pr view <num> --json mergeable,mergeStateStatus` to verify `MERGEABLE` / `CLEAN`—rebasing immediately if the base advanced—then share the link and wait. Keep open PR titles, descriptions, labels, and Milestones synced on every push/rebase, and format PR links with titles as `[#NNN — PR Title](https://github.com/shthed/capy/pull/NNN)` and Epic references as `[EPIC-N](https://github.com/shthed/capy/issues/<num>)` per [`PROJECT.md`](./PROJECT.md).
2. **Build Android freely; never install unprompted**: Run `./gradlew app:testDebugUnitTest`, `./gradlew app:buildWeb`, and `./gradlew app:assembleDebug` freely; never run `./gradlew app:installDebug` unless explicitly requested.
3. **Always display detailed thoughts & visible status updates**: Continuously explain what file/system is inspected, why, and what was learned—both in thinking blocks and concise present-participle chat updates ("Inspecting...", "Verifying...", "Updating...").
4. **Enforce [`DEV.md` Section 5](./DEV.md#5-core-technical-guardrails-web--app) before coding**: Uphold all Web/Canvas/Worker/Bridge/Kotlin invariants in [`DEV.md`](./DEV.md).
5. **Verify builds before pushing code**: Always pass `npm run test:sanity`, `npm run lint`, and `npm run build` cleanly before opening or updating code PRs.
6. **Strict doc, `ROADMAP.md`, `[EPIC-1]`--`[EPIC-5]` & Sprint `TODO.md` sync, zero emojis & no ASCII art**: Never use emojis or box-drawing art in `.md` files. Verify source names before documenting (avoid unpinned `#L...` line numbers inside `.md` guides). Keep [`TODO.md`](./TODO.md) strictly scoped to active-sprint ready tasks per [`PROJECT.md`](./PROJECT.md#2-lean-agile-lifecycle-and-backlog-governance) (delete finished `BUG-*`/`TASK-*` immediately—never `[x]`), enforce **`1-Issue-per-Epic` ([EPIC-1](https://github.com/shthed/capy/issues/476)--[EPIC-5](https://github.com/shthed/capy/issues/480))** (check off `- [x] [#NNN — Title/Summary](https://github.com/shthed/capy/pull/NNN)` sorted numerically per group via `gh issue edit` when Epic slices ship; never open separate Issues for `TASK-*`, Sprint `BUG-*`, or `ICE-*` unless asked), move finished Stories/Epics into the collapsed `<details>` **Shipped Epics & Stories** archive at the bottom of [`ROADMAP.md`](./ROADMAP.md) with clickable `[#NNN — PR Title](https://github.com/shthed/capy/pull/NNN)` links, and sync [`PROJECT.md`](./PROJECT.md), [`DEV.md`](./DEV.md), [`ROADMAP.md`](./ROADMAP.md), [`WEB.md`](./WEB.md), [`PUZZLE.md`](./PUZZLE.md), [`APP.md`](./APP.md), [`CLOUD.md`](./CLOUD.md), [`TESTING.md`](./TESTING.md), [`CHANGELOG.md`](./CHANGELOG.md), and [`README.md`](./README.md).
7. **Report `>= 95%` PR Readiness Score at the end of PRs (`<details>` + `%`-first `PR Readiness Checklist` + closing rationale)**: Evaluate every PR using a variable-length **PR Readiness Checklist** scored strictly as percentages (`0%--100%`, never fixed-weight fractions and never capped at 5 items—include as many or as few scope-relevant criteria lines as the PR requires). Auto-fix technical/test/doc gaps and resolve ambiguity (`/grill-me`) until overall readiness is `>= 95%`. Place `### PR Readiness Score: <N>%` at the **end** of the PR description (and PR Summary comment), wrap the detailed **PR Readiness Checklist** inside `<details><summary>PR Readiness Checklist</summary>...</details>` (with blank lines after `</summary>` and before `</details>`, showing `%` at the start of each line item like `- **100%** — **<Criterion>**: <Verification summary>`), and finish with a brief closing note explaining why the PR is complete/ready (or stating the exact `-N%` gap if `< 100%`, followed **only** when `< 100%` by a `- [ ] ...` checklist of remaining [`TODO.md`](./TODO.md) subtasks scoped for inclusion in *this* PR—never list unrelated backlog tasks on a `100%` complete PR). Also report the score in your chat merge request.
8. **Mobile-first formatting (never output wide tables)**: Never respond in chat, artifacts, PR comments, or `.md` files with wide multi-column tables or prose-heavy cells that overflow mobile screens into empty whitespace. Use compact structured bullet lists instead; reserve tables strictly for 2 short-value columns that fit narrow phone screens without scrolling.
9. **Regularly check `~/.gemini/WHITEBOARD.md` and live GitHub for updates & actions**: Check `~/.gemini/WHITEBOARD.md` AND live GitHub (`gh pr list --state open`, `gh run list`, active PR checks/reviews/comments, and [EPIC-1](https://github.com/shthed/capy/issues/476)--[EPIC-5](https://github.com/shthed/capy/issues/480) Issues) at session/task start, regularly during multi-step work, and before status updates, handoffs, or release decisions so Owner directives, peer chat notes, new/updated PRs, CI results, and pending actions (such as independent AI reviews, conflict rebases, or held PRs) are acted on promptly. When coordinating across top-level chats, update only your own role's section of `~/.gemini/WHITEBOARD.md` (plus `Open Notes / Handoff Queue` if needed) with a UTC timestamp whenever your status changes or you reach a milestone.
10. **Clickable PR & Issue links with titles (`[#NNN — PR Title](...)`)**: Whenever referencing a PR or Issue in chat responses, PR descriptions/comments, status notes, or `.md` reviews, ALWAYS format it as a clickable markdown link containing both the number and title (for example, `[#NNN — PR Title](https://github.com/shthed/capy/pull/NNN)` or `[EPIC-N — Title](https://github.com/shthed/capy/issues/NNN)`), never bare `#NNN` without a clickable link and title (preserving [`CHANGELOG.md`](./CHANGELOG.md)'s trailing `[#NNN](https://github.com/shthed/capy/pull/NNN)` bullet suffix where bullet prose already summarizes the PR).
11. **Push [`AGENTS.md`](./AGENTS.md) changes directly to `main` immediately (never in PRs)**: Always commit and push approved [`AGENTS.md`](./AGENTS.md) edits directly to `main` immediately using Repository admin bypass, never inside feature or docs PRs against `beta` where divergent branches create merge conflicts and delay active-session adoption; immediately back-merge `main -> beta` (`--merge`, never `--squash`) so `beta` stays synced and `beta -> main` Release Promotion PRs remain conflict-free.

## 2. Token Efficiency & Context Discipline

- **On-Demand Doc Loading**: Load [`PROJECT.md`](./PROJECT.md) (for PM/PR/backlog/release tasks) or [`DEV.md`](./DEV.md) plus only the subsystem `.md` matching Section 3—never all `.md` guides upfront.
- **Search Before Sliced Reads**: Run `grep` first, then `view_file` narrow `StartLine`/`EndLine` slices (`<= 150` lines) rather than whole large files.
- **Parallel Batching & Full Local VM Verification**: Batch independent reads/edits in parallel, then run `npm run test:sanity && npm run lint && npm run build && npm test` once at the end inside the Antigravity VM (daily `feature/* -> beta` CI stays fast/minimal while non-draft `beta -> main` Release Promotion PRs also run the Playwright E2E CI gate).
- **Subagent Isolation**: Use `research` subagents (`Model: 'inherit'`, `Workspace: 'inherit'`) only for broad multi-file surveys; do 1–3 file lookups directly.
- **Zero-Rebuild Docs Fast-Path**: Pure `.md` PRs pass `Build & Test` in `< 2s` (skipping Web/Android compilation and Pages deploy) and do not bump `web/package.json` (append the clickable `[#NNN](https://github.com/shthed/capy/pull/NNN)` bullet under the current channel heading in [`CHANGELOG.md`](./CHANGELOG.md) and run `npm run test:sanity` locally).

## 4. AI Git, Bookmark & PR Readiness Protocol

- **3-Tier Pipeline (`feature/* -> beta -> main`), Draft-First PRs, Zero Conflicts & Worktree Isolation**: Always `git fetch --all --prune`, branch/worktree cleanly and linearly onto updated `origin/beta` (`feature/*`, `automation/sprint-*`, `fix/*`, `docs/*`—never edit inside a shared dirty primary checkout across concurrent sessions) and open WIP PRs as `--draft` (`--base beta`, except explicit `beta -> main` Release Promotion PRs; if `origin/beta` is not yet initialized, verify with the user before pushing `origin/main:refs/heads/beta`). Check `gh pr view <num> --json mergeable,mergeStateStatus` on every update so PRs never sit `CONFLICTING` or stale behind their base. Default to `1-Task = 1-PR` in single chats, or group atomic per-task commits for a cohesive Story/Sprint slice onto one `automation/sprint-*` or `feature/*` PR under `/goal` or `/teamwork` per [`PROJECT.md` Section 4](./PROJECT.md#4-pull-request-lifecycle-and-readiness-gates). Keep diffs minimal; never commit secrets.

- **Bot-Authored Draft PRs ([`open-pr.yml`](./.github/workflows/open-pr.yml)) & CI Triggers**: Open PRs authored by `github-actions[bot]` via `gh workflow run open-pr.yml -f head=<branch> -f base=beta -f title="..." -f body="..." -f draft=true -f labels="..." -f milestone="..."` (using `gh pr create` only as a one-time fallback before `open-pr.yml` exists on `main`). Because `GITHUB_TOKEN` PR creation does not emit `pull_request: opened`, leave `draft=true` at creation and run `gh pr ready <num>` (emits `pull_request: ready_for_review` to trigger `Build & Test`, `Deploy to GitHub Pages`, `Playwright E2E Release Gate` on `main`, and `Dual AI & Owner Review Gate`), push follow-up commits (`synchronize`), or run `gh workflow run deploy-branch.yml -f target_branch=<branch>` for WIP Draft previews.
- **Dual AI & Owner PR Review Gate ([`pr-review-gate.yml`](./.github/workflows/pr-review-gate.yml))**: After verification passes, run `gh pr ready <num>` FIRST, then post an independent read-only Reviewer verdict (`gh pr review <num> --comment` containing `<!-- capy-review: actor=ai-agent verdict=APPROVED sha=<40_CHAR_HEAD_SHA> score=<SCORE>% -->` with `<SCORE> >= 95`), then add `review:ai-approved`. On `github-actions[bot]`-opened PRs, the Project Owner unlocks merge with a 1-click native GitHub **Approve** review (empty comment allowed; `review:owner-approved` or `APPROVED`/`LGTM` comments alone hold `capy/review-gate` at `pending` awaiting the native Approve click, and `pr-review-gate.yml` skips bot self-approval to avoid HTTP 422; manual owner-authored PRs preserve legacy `review:owner-approved` and `APPROVED`/`LGTM` fallback). NEVER apply `review:owner-approved` or post human `APPROVED`/`LGTM` comments on behalf of the Project Owner unless explicitly instructed.

- **Human-Understandable `## Summary` at the Very Top of Every PR**: Start every PR description on line 1 (*above* preview/test links, Agile scope metadata, technical overview bullets, and code diffs) with a short `## Summary` section (`1`--`3` plain-English sentences or everyday bullets) written for a non-technical reader explaining what changes for players or the project and why. Keep commit SHAs, file paths, React/API symbol names, CLI commands/flags, CI workflow/job IDs, and internal jargon out of this top summary—place preview/Beta/test links, Agile scope, and technical details underneath it.
- **Clean PR Titles, GitHub Agile Metadata, PR Sync-on-Push & Bookmarks**: Write clean, prefix-free action-oriented PR titles (never put `feat():`, `EPIC-*`, or laundry lists in titles). Attach GitHub Labels (`epic:1`..`epic:5` for Epic slices—omit `epic:*` on standalone P0 `BUG-*` fixes; plus `web`, `android`, `feature`, `fix`, `docs`, `ui`, `testing`, `ci`, `deps`), assign the active GitHub Sprint Milestone (`Sprint N: ...`), and place below the top `## Summary` the preview link `https://shthed.github.io/capy/alpha/<number>/` (plus live **Beta** `https://shthed.github.io/capy/beta/` & `https://shthed.github.io/capy/beta/capy.apk` on Release Promotion PRs) + clickable **Test Results** links (GitHub Actions `Build & Test`, `Playwright E2E Release Gate`, and review-gate check/run URLs updated for the final HEAD SHA) + `**Agile Scope**: Tracked in [EPIC-N](https://github.com/shthed/capy/issues/<num>) (...)` (**never** use `Closes #<epic-issue>` or `Fixes #<epic-issue>` on partial Epic PRs, which prematurely auto-closes the Parent Epic Issue—close only when `100%` of the Epic ships to `main`), followed by scannable technical overview bullets explaining what and *why* and commit-pinned change bullets. Always refer to Epics as `[EPIC-N](https://github.com/shthed/capy/issues/<num>)` (never bare/backticked `#<epic-issue>` or `[#<epic-issue>](.../issues/...)`) and PRs as clickable `[#NNN — PR Title](https://github.com/shthed/capy/pull/NNN)` links. Immediately update PR title, overview bullets, SHA-pinned links, labels, and Milestone whenever follow-up commits or rebases alter scope, version, or conflict status. Check off completed `- [x] [#NNN — Title/Summary](https://github.com/shthed/capy/pull/NNN)` items in [EPIC-1](https://github.com/shthed/capy/issues/476)--[EPIC-5](https://github.com/shthed/capy/issues/480) upon merge. Create `PR_<num>.url.json` (`UserFacing: true`) titled `#<num> <PR Title>`.
- **Versioning, Changelog Channel Markers & Links**: Bump `"version"` in [`web/package.json`](./web/package.json) (`MAJOR*10000 + MINOR*100 + PATCH`) on code PRs and add a flat single-bullet [`CHANGELOG.md`](./CHANGELOG.md) entry ending in a clickable `[#NNN](https://github.com/shthed/capy/pull/NNN)` PR link (never unlinked `#NNN` or parentheses) under compact `### X.Y - YYYY-MM-DD` (or `### X.Y.Z - YYYY-MM-DD` whenever `main` and `beta` diverge on patch versions under the same `X.Y`) carrying the active channel suffix (`(Alpha)`, `(Beta)`, `(Production)`, or `(Production, Beta)`—historical superseded headings stay untagged; enforced by `npm run test:sanity` and `npm test` in [`PROJECT.md` Section 5](./PROJECT.md#5-release-promotion-and-changelog-governance) and [`DEV.md` Section 8](./DEV.md#8-versioning-dependency-maintenance--asset-playbooks)). Document new settings; prune dead refs; pin PR/comment line links to SHAs.
- **End-of-PR Readiness Checklist (`>= 95%`, `%`-First & Flexible Criteria)**: Include as many or as few scope-relevant criteria lines as the PR requires (no 5-item cap)—drawing from core checks (**Functionality & Edge Cases**, **Automated Tests**, **Performance & Golden Invariants**, **Docs & Changelog Sync**, **CI, Mergeability & Preview Verification** (`MERGEABLE` / `0` conflicts against base branch)) plus domain checks (**Accessibility & Mobile Layout**, **Android / Bridge Parity**, **Cloud Sync / Worker Safety**, **CI / Workflow Hygiene**, etc.) whenever relevant. Place `### PR Readiness Score: <N>%` at the **end** of the PR body and Development Summary PR comment, wrap the checklist inside `<details><summary>PR Readiness Checklist</summary>` (with blank lines after `</summary>` and before `</details>`, showing `%` at the start of each line item like `- **100%** — **<Criterion>**: <Verification summary>`), and follow `</details>` with a concise closing note explaining why the PR is complete/ready (or stating the `-N%` gap, plus a `- [ ] ...` checklist of remaining [`TODO.md`](./TODO.md) subtasks scoped for inclusion in *this* PR **only** when `< 100%`) per [`PROJECT.md` Section 4](./PROJECT.md#4-pull-request-lifecycle-and-readiness-gates).
